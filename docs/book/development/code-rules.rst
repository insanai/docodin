.. _code-rules:

==========
Code rules
==========

docodin's code follows a few firm rules.  DOD 11 records why; this chapter is the
checklist.

Size
====

- **Files** have at most **1408 lines**.  Split a growing module by topic into private
  submodules, and re-export the public names where docutils expects them.
- **Lines** have at most **99 characters**, and never more than **108**.  ruff enforces
  108 for Python (``line-length = 108``); keep to 99 in review, in Odin as in Python.
- **Procedures and functions** are short and simple.  For Python, ruff enforces a
  cyclomatic complexity of at most 12, at most 14 branches, 50 statements and 8 return
  statements.  Odin code keeps to the same limits by review: split long procedures into
  named steps.

Check Python with:

.. code-block:: console

   $ uv run ruff check python tests scripts

Odin
====

- Build with ``-vet -strict-style``; the build script does.
- Use data-oriented design: handles (``distinct u32``) instead of pointers, ``#soa``
  arrays for hot fields, side tables for cold ones, arenas, interned strings or views
  into the source.
- Keep bounds checks on.  Keep tables ``@(rodata)``.  No shared mutable state.
- Bound recursion explicitly, and report an error message where docutils would fail with
  a ``RecursionError``.
- Mutate document trees only through the ``doctree`` procedures.

Python
======

- Idiomatic, typed Python with ``from __future__ import annotations``.
- In the docutils package, keep docutils' public names, signatures, ``__module__`` paths
  and exception texts.  Message texts mirror docutils' ``%``-formatting (ruff's ``UP031``
  is off for that reason).
- Run Python through ``uv run``, never a system interpreter.

Generated code
==============

Tables and data that come from docutils or from Python are generated by
``scripts/gen_*.py`` and carry a header that names the generator.  Change the generator,
not the output.

Messages
========

- docodin's own tools (the native commands, the checker, the ``docodin dod`` and
  ``docodin book`` commands) report problems in the Elm style: a titled report, the
  source excerpt with markers, a plain explanation and a hint (DOD 5).
- Everything on the docutils path keeps docutils' exact message texts, and the tools keep
  ``--error-format=docutils``.

Fidelity
========

Every change that touches the docutils path comes with the differential test that shows
it identical.  A performance change keeps the parse-tree hash identical.

Commits
=======

- One logical change per commit, small enough to review on its own.
- The message is a short, plain sentence that says what the commit changes.  Refer to
  issues or pull requests only when needed.
- No trailers, and no tool, assistant, company or product attributions in commit
  messages or metadata.
- Each commit builds, and passes the tests it touches.
