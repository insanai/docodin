# docodin 0.2.0: design memo

Status: proposal. Scope: what docodin should take from tree-sitter, ruff,
rust-analyzer and the fast Markdown parsers, measured against where the native
parser spends its time today.

The hard constraint does not move: **the docutils path (the shim, `docodin_parse`
and the wire format it feeds, the native pipeline's outputs) stays byte for byte
identical to docutils 0.22.4.** Every item below is either invisible to that
path, or is an internal speed-up that is proven identical by the existing
differential suites plus a parse-tree hash comparison.

## 1. Summary

- The parser is fast enough for an editor today. The largest real document in
  docutils' own docs (`ref/rst/restructuredtext.rst`, 124 KB) parses in 1.7 ms,
  and the 60 files of the docs tree check in 10–20 ms. rust-analyzer, ruff and
  ty all do a **full reparse per edit**. docodin should too, first, and add
  incremental reuse only where measurement demands it.
- What editors lack is not speed but **positions**. The parse tree has a line
  per node and no byte ranges, no end positions and no columns. A lossless
  position layer is the prerequisite for semantic tokens, folding, go-to-
  definition, hover, code actions, and for any later incremental reuse.
- Profiling (section 3) shows that about 60 % of parse time is in the inliner,
  and most of it in one waste: every word start runs the full `simplename`
  match and the standalone-URI/e-mail match. Two exact pre-filters and a SIMD
  line splitter, tried in a scratch copy, cut the 20.9 MB parse from 386 ms to
  225 ms (**1.7×**, instructions 3.95 G → 2.47 G) with an identical parse tree.
- reST's block structure is anchored at column 0 and separated by blank lines,
  and the state between top-level constructs is nearly empty. That makes a
  tree-sitter-style "reparse until the state converges, then splice" strategy
  much simpler for reST than for Python, provided the construct classes that
  continue across blank lines are handled (section 5).
- A native `docodin-lsp` modelled on ruff server is the main 0.2.0 feature. It
  uses the Elm-style diagnostics that `odin/check` already has, and it gives
  editors docutils-exact structure where tree-sitter-rst is known to be wrong.

## 2. Findings

### 2.1 tree-sitter

- **Relative positions.** Each `Subtree` stores `padding` and `size` as
  `{bytes, row, column}`, and absolute positions are summed while walking, so an
  edit touches only the nodes on its path. Small leaves live inline in the
  8-byte handle, and children sit directly before their parent's data
  ([subtree.h](https://github.com/tree-sitter/tree-sitter/blob/master/lib/src/subtree.h)).
- **Edits.** `ts_tree_edit` marks the nodes on the path `has_changes`. A child
  counts as untouched only if `end + lookahead_bytes < edit.start`, where
  `lookahead_bytes` is how far the lexer *peeked* past the token. A token whose
  scanner asked for its column (`depends_on_column`) is invalidated when the
  column shifts ([subtree.c `ts_subtree_edit`](https://github.com/tree-sitter/tree-sitter/blob/master/lib/src/subtree.c)).
- **Reuse.** `ReusableNode` walks the old tree in step with the parser. A node
  is reused only if it starts at the current byte, is unchanged, not an error
  and not *fragile* (built under a GLR conflict), the external-scanner state
  before it equals the current one byte for byte, its first leaf's lex mode
  matches, and the GLR stack has one version
  ([parser.c `ts_parser__reuse_node`](https://github.com/tree-sitter/tree-sitter/blob/master/lib/src/parser.c)).
  The algorithm descends from Wagner & Graham, TOPLAS 1998
  ([pdf](https://harmonia.cs.berkeley.edu/papers/twagner-parsing.pdf)).
  `ts_tree_get_changed_ranges` diffs the old and new trees for re-highlighting
  ([get_changed_ranges.c](https://github.com/tree-sitter/tree-sitter/blob/master/lib/src/get_changed_ranges.c)).
- **Error recovery** is cost-based: skipping a character costs 1, skipping a
  tree 100, a missing tree 110, recovery 500. The parser tries, in order,
  inserting one MISSING token, popping back to an earlier state, and skipping
  into an ERROR node, with at most 6 stack versions
  ([error_costs.h](https://github.com/tree-sitter/tree-sitter/blob/master/lib/src/error_costs.h)).
- **External scanners** must serialize their *entire* state, at most 1024
  bytes, after every external token; it is restored before the next scan
  ([docs](https://github.com/tree-sitter/tree-sitter/blob/master/docs/src/creating-parsers/4-external-scanners.md)).
  tree-sitter-python's state is an indent stack of `uint16`, a string-delimiter
  stack and a flag. It emits INDENT when a line is deeper than the top, one
  zero-width DEDENT per call while it is shallower, none inside brackets, and
  counts a tab as a flat +8
  ([scanner.c](https://github.com/tree-sitter/tree-sitter-python/blob/master/src/scanner.c)).
- **Queries.** `highlights.scm`, `locals.scm` and `injections.scm` are pattern
  files. The host evaluates predicates such as `#match?` and `#any-of?`.
  Injections re-parse embedded ranges as another language. tree-sitter-highlight
  itself re-parses from scratch
  ([docs](https://github.com/tree-sitter/tree-sitter/blob/master/docs/src/3-syntax-highlighting.md),
  [highlight.rs](https://github.com/tree-sitter/tree-sitter/blob/master/crates/highlight/src/highlight.rs)).

### 2.2 tree-sitter-rst

[stsewd/tree-sitter-rst](https://github.com/stsewd/tree-sitter-rst) is a
~1600-line hand-written scanner behind a small grammar. 45 of its tokens are
external, and each inline construct (`*emphasis*` from start to end) is one
opaque token
([tokens.h](https://github.com/stsewd/tree-sitter-rst/blob/master/src/tree_sitter_rst/tokens.h),
[parser.c](https://github.com/stsewd/tree-sitter-rst/blob/master/src/tree_sitter_rst/parser.c)).
Where it differs from docutils:

- **Sections are flat**: only titles, "to avoid guessing the level of
  subtitles". Underline length is not checked
  ([README](https://github.com/stsewd/tree-sitter-rst/blob/master/README.md),
  [#43](https://github.com/stsewd/tree-sitter-rst/issues/43)).
- **Unimplemented**: tables, option lists, blank lines between list items
  ([#29](https://github.com/stsewd/tree-sitter-rst/issues/29)) and nested line
  blocks.
- **Lists**: enumerator sequence and style are not checked.
- **Directive content** is opaque. Editors re-inject it as reST by directive
  name, which misses nested directives
  ([#51](https://github.com/stsewd/tree-sitter-rst/issues/51),
  [#52](https://github.com/stsewd/tree-sitter-rst/issues/52)).
- **Blank lines are required** after every block: a missing one before a
  title swallows the title ([#47](https://github.com/stsewd/tree-sitter-rst/issues/47)),
  and an incomplete definition list eats the rest of the file
  ([#48](https://github.com/stsewd/tree-sitter-rst/issues/48)).
- **Incremental parsing**: the only serialized state is the indent stack, and
  serialize/deserialize were broken until
  [PR #70](https://github.com/stsewd/tree-sitter-rst/pull/70) (June 2026), which
  explains [#44](https://github.com/stsewd/tree-sitter-rst/issues/44) and
  [#64](https://github.com/stsewd/tree-sitter-rst/issues/64). Heavy multi-line
  peeking gives large `lookahead_bytes`, so edits invalidate far. Tabs count a
  flat +8 instead of tab stops.
- **Queries** are not shipped. Neovim
  ([highlights.scm](https://github.com/nvim-treesitter/nvim-treesitter/blob/main/runtime/queries/rst/highlights.scm)),
  Zed ([zed-rst](https://github.com/elmarco/zed-rst/blob/main/extension.toml))
  and Helix each carry their own.

Lesson: an approximate grammar can colour reST, but it cannot give an editor
docutils' structure. That structure should come from the exact parser, over LSP.

### 2.3 ruff's parser and ruff server

- **Parser.** A hand-written recursive descent parser replaced LALRPOP in ruff
  0.4.0. It is ">2x faster" (large/dataset.py: 63.6 → 26.6 ms) and made
  linting and formatting 20–40 % faster
  ([blog](https://astral.sh/blog/ruff-v0.4.0),
  [PR #10036](https://github.com/astral-sh/ruff/pull/10036)).
- **Lexer.** Lazy, and able to re-lex a token in a new context (+28 %,
  [PR #11457](https://github.com/astral-sh/ruff/pull/11457)).
  `checkpoint()`/`rewind()` save lexer state and error count for speculative
  parsing; an unclosed bracket is recovered by re-lexing the last newline as a
  logical one ([PR #11845](https://github.com/astral-sh/ruff/pull/11845)).
- **Tokens.** `Tokens` is a lossless `Vec<Token{kind, range, flags}>` that
  keeps comments and non-logical newlines. Comment ranges and indentation style
  are derived from it
  ([tokens.rs](https://raw.githubusercontent.com/astral-sh/ruff/main/crates/ruff_python_ast/src/token/tokens.rs)).
- **Positions.** Offsets are `TextSize(u32)` UTF-8 byte offsets, paired into
  `TextRange`. `LineIndex` keeps line starts, with an ASCII fast path, and
  binary-searches them to convert an offset to UTF-8, UTF-16 or UTF-32 columns,
  as LSP requires
  ([line_index.rs](https://raw.githubusercontent.com/astral-sh/ruff/main/crates/ruff_source_file/src/line_index.rs)).
- **Errors never stop the parse.** The result `Parsed<T>` carries the syntax
  tree, the tokens and the errors. A 32-bit `RecoveryContext` set decides
  whether an unexpected token ends the current list or is skipped with an
  error. An error at the same offset as the previous one is dropped
  ([parser/mod.rs](https://raw.githubusercontent.com/astral-sh/ruff/main/crates/ruff_python_parser/src/parser/mod.rs)).
- **AST.** Nodes are boxed. A `u32` `node_index`, assigned after parsing, lets
  ty keep `AstNodeRef`s without holding whole ASTs, which had cost "multiple GB"
  ([node_index.rs](https://raw.githubusercontent.com/astral-sh/ruff/main/crates/ruff_python_ast/src/node_index.rs),
  [#15621](https://github.com/astral-sh/ruff/issues/15621)). docodin's `#soa`
  tree with `u32` handles is already there.
- **ruff server.** Sources:
  [server.rs](https://raw.githubusercontent.com/astral-sh/ruff/main/crates/ruff_server/src/server.rs),
  [schedule.rs](https://raw.githubusercontent.com/astral-sh/ruff/main/crates/ruff_server/src/server/schedule.rs),
  [text_document.rs](https://raw.githubusercontent.com/astral-sh/ruff/main/crates/ruff_server/src/edit/text_document.rs),
  [lint.rs](https://raw.githubusercontent.com/astral-sh/ruff/main/crates/ruff_server/src/lint.rs).
  `lsp_server` with a main loop fed by a bounded channel; notifications run
  synchronously, diagnostics, hover and code actions on a thread pool over
  copy-on-write snapshots. Sync is incremental (each change converted through
  `LineIndex`, applied with `replace_range`, index rebuilt). Diagnostics are
  pulled, or pushed for older clients. **Every lint re-lexes and reparses the
  whole file.** Quick fixes travel in the diagnostic's `data`.
- **ty** puts its incrementality in salsa, but its parse query is `no_eq`: every
  edit reparses the file
  ([parsed.rs](https://raw.githubusercontent.com/astral-sh/ruff/main/crates/ruff_db/src/parsed.rs),
  [ty](https://astral.sh/blog/ty)).

### 2.4 Zed

Zed reparses with tree-sitter on every edit:

`Buffer::reparse` gives the parse 1 ms synchronously, then finishes it in the
background and parses again if the buffer changed meanwhile. Injection layers
live in a copy-on-write sum tree, and `interpolate()` shifts old trees with
`tree.edit` so stale highlights stay aligned until the new parse lands.
Sources: [buffer.rs](https://raw.githubusercontent.com/zed-industries/zed/main/crates/language/src/buffer.rs),
[syntax_map.rs](https://raw.githubusercontent.com/zed-industries/zed/main/crates/language/src/syntax_map.rs),
[blog](https://zed.dev/blog/syntax-aware-editing).

Each language feature (highlights, brackets, outline, indents, injections,
textobjects) is a query file. The language server is a separate process that
the extension launches with `language_server_command`
([docs](https://zed.dev/docs/extensions/languages)). The pattern is
tree-sitter for instant, approximate local structure, and the server for exact
answers.

### 2.5 rust-analyzer and rowan

- **Parser.** Hand-written recursive descent that emits `Start`, `Finish`,
  `Token` and `Error` events into a separate builder. "Parsing never fails"
  ([architecture.md](https://raw.githubusercontent.com/rust-lang/rust-analyzer/master/docs/book/src/contributing/architecture.md)).
- **Green nodes** are immutable, store only widths, give children relative
  offsets, and are deduplicated, which saves 17 % of their memory. **Red
  nodes** are created lazily with a parent pointer and an absolute offset
  ([green/node.rs](https://raw.githubusercontent.com/rust-analyzer/rowan/master/src/green/node.rs),
  [node_cache.rs](https://raw.githubusercontent.com/rust-analyzer/rowan/master/src/green/node_cache.rs),
  [cursor.rs](https://raw.githubusercontent.com/rust-analyzer/rowan/master/src/cursor.rs)).
- **Incremental reparsing** re-lexes a single token if it keeps its kind, else
  reparses the nearest balanced `{}` block, else the whole file
  ([reparsing.rs](https://raw.githubusercontent.com/rust-lang/rust-analyzer/master/crates/syntax/src/parsing/reparsing.rs)).
  The team's verdict is that "incremental reparsing doesn't actually matter
  much for IDE use-cases"
  ([syntax.md](https://raw.githubusercontent.com/rust-lang/rust-analyzer/master/docs/book/src/contributing/syntax.md)),
  and the block heuristic "is not actually enabled still"
  ([matklad](https://lobste.rs/s/ws0mt8/structured_editing_incremental_parsing)).
- **salsa** memoizes queries with their dependencies; *backdating* stops
  invalidation when a recomputed value is unchanged (early cutoff), and
  *durability* levels skip revalidating rarely-changing inputs. Sources: [algorithm](https://salsa-rs.github.io/salsa/reference/algorithm.html),
  [durability](https://rust-analyzer.github.io/blog/2023/07/24/durable-incrementality.html).
  "Three architectures for a responsive IDE" gives per-file map-reduce indexing
  as the simplest design that scales
  ([post](https://rust-analyzer.github.io/blog/2020/07/20/three-architectures-for-responsive-ide.html)).
  The resilient-LL tutorial adds two rules: every loop iteration consumes input,
  and recovery sets decide where an error ends
  ([tutorial](https://matklad.github.io/2023/05/21/resilient-ll-parsing-tutorial.html)).

### 2.6 Fast markup parsers and SIMD scanning

- **pulldown-cmark** parses in two passes.
  - Pass 1 builds the block structure as a `Vec` tree with index links: slot 0
    is a dummy and `TreeIndex` is `NonZeroUsize`, the same layout as docodin's.
    Paragraph content stays a chain of "maybe inline" items.
  - Pass 2 resolves inlines lazily, one block at a time.
  - Every item carries `start` and `end` offsets, and `into_offset_iter()`
    yields ranges.
  - `lower_bounds[11]` implements CommonMark's `openers_bottom` rule, which
    keeps emphasis matching linear.
  - **SIMD**: 16 bytes are classified against the special-byte set with two
    `pshufb` nibble lookups (`lut[b & 15] |= 1 << (b >> 4)`); the resulting
    bitmask is walked with `trailing_zeros`, and newlines are found with
    `memchr2`. It is reported to more than double scanning speed, for about
    10 % overall
    ([fullyfaithful.eu](https://fullyfaithful.eu/simd-byte-scan/), search
    snippet only).

  Sources: [issue #41](https://github.com/raphlinus/pulldown-cmark/issues/41),
  [firstpass.rs](https://raw.githubusercontent.com/pulldown-cmark/pulldown-cmark/master/pulldown-cmark/src/firstpass.rs),
  [parse.rs](https://raw.githubusercontent.com/pulldown-cmark/pulldown-cmark/master/pulldown-cmark/src/parse.rs),
  [0x80.pl](http://0x80.pl/articles/simd-byte-lookup.html).
- **md4c** uses push callbacks and no AST. Per block it first collects "all
  potentially meaningful marks" into a compact buffer, and barely validates
  Unicode: 0.365 s against cmark's 0.706 s, 41 allocations against 3.9 M.
  Sources: [md4c](https://github.com/mity/md4c),
  [notes](https://talk.commonmark.org/t/why-is-md4c-so-fast-c/2520),
  [cmark benchmarks](https://raw.githubusercontent.com/commonmark/cmark/master/benchmarks.md).
  The CommonMark appendix describes the same shape: a block phase, then a
  delimiter stack with `openers_bottom`. cmark checks linear time with
  `pathological_tests.py` under a timeout
  ([spec](https://raw.githubusercontent.com/commonmark/commonmark-spec/master/spec.txt),
  [tests](https://raw.githubusercontent.com/commonmark/cmark/master/test/pathological_tests.py)).
  comrak uses an arena of `RefCell` nodes and is slow
  ([comrak](https://github.com/kivikakk/comrak)). markdown-rs emits events in
  which "every byte is accounted for, with positional info"
  ([readme](https://raw.githubusercontent.com/wooorm/markdown-rs/main/readme.md)).
- **djot** is designed for linear time "with no backtracking". References never
  depend on later definitions, and the syntax needs no Unicode classes. Its
  inline parser keeps a stack of openers
  ([djot](https://github.com/jgm/djot),
  [inline.ts](https://raw.githubusercontent.com/jgm/djot.js/main/src/inline.ts)).
  reST has none of these properties (section 4), hence docodin's memo tables.
- **simdjson** stage 1 works on 64-byte blocks without branches. Two
  `vpshufb` nibble tables classify each byte, quoted ranges come from a
  carry-less multiply, and `tzcnt`/`blsr` extract the indices
  ([Langdale & Lemire](https://arxiv.org/pdf/1902.08318)). UTF-8 can be
  validated in under one instruction per byte
  ([Keiser & Lemire](https://arxiv.org/abs/2010.03090)).
- **memchr** does splat, `cmpeq`, movemask and `trailing_zeros`, 64 bytes per
  iteration. On aarch64 movemask is emulated with `vshrn_n_u16`. Its SWAR
  fallback is `(x - 0x01…) & ~x & 0x80…`
  ([memchr.rs](https://raw.githubusercontent.com/BurntSushi/memchr/master/src/arch/generic/memchr.rs),
  [vector.rs](https://raw.githubusercontent.com/BurntSushi/memchr/master/src/vector.rs)).
- **Odin `core:simd`** covers all of this portably on NEON and SSE/AVX:
  `#simd[N]T` vectors, `lanes_eq`/`lt`/`ge`, `select`, `reduce_or`/`min`,
  `extract_msbs` (movemask), `runtime_swizzle` (`tbl`/`pshufb`, i.e. the nibble
  classifier), `count_trailing_zeros`, and raw intrinsics in `core:simd/x86`
  and `core:simd/arm`. `strings.index_byte` is already vectorised
  ([simd.odin](https://raw.githubusercontent.com/odin-lang/Odin/master/core/simd/simd.odin),
  [bytes.odin](https://raw.githubusercontent.com/odin-lang/Odin/master/core/bytes/bytes.odin)).

### 2.7 reST editor tooling today

- **esbonio** ([repo](https://github.com/swyddfa/esbonio), v2.1.0) is the only
  reST language server with completion, hover, definition and symbols.
  - It is a pygls server. Its features run in a "sphinx agent" subprocess
    injected into the user's environment
    ([sphinx processes](https://raw.githubusercontent.com/swyddfa/esbonio/develop/docs/integrating/reference/sphinx-processes.rst)).
  - Its diagnostics are Sphinx log warnings, collected after a build
    ([diagnostics.py](https://raw.githubusercontent.com/swyddfa/esbonio/develop/lib/esbonio/esbonio/sphinx_agent/handlers/diagnostics.py)).
  - It has no semantic tokens, folding, references or rename.
- **Editors**: VS Code (lextudio) = TextMate grammar + esbonio + rstcheck/doc8
  ([README](https://raw.githubusercontent.com/vscode-restructuredtext/vscode-restructuredtext/master/README.md));
  Zed = tree-sitter-rst + esbonio ([docs](https://zed.dev/docs/languages/rst));
  Neovim = nvim-treesitter ("unstable" tier, no folds) + esbonio via lspconfig
  ([esbonio.lua](https://raw.githubusercontent.com/neovim/nvim-lspconfig/master/lsp/esbonio.lua)).
- **Others**: snooty-parser vendors docutils' parser, declares directives in
  `rstspec.toml` and has a diagnostics-only server
  ([language_server.py](https://raw.githubusercontent.com/mongodb/snooty-parser/main/snooty/language_server.py));
  rust-rst is a PEG subset ([repo](https://github.com/flying-sheep/rust-rst));
  rstcheck, restructuredtext-lint and doc8 wrap docutils' messages; sphinx-lint
  is regex-based ([README](https://raw.githubusercontent.com/sphinx-contrib/sphinx-lint/main/README.md)).
- **What nobody provides** for reST: diagnostics as you type from the exact
  grammar without a Sphinx build, semantic tokens, folding, references and
  rename, hover for substitutions and footnotes, and completion of a
  document's own targets. docodin already has the grammar, the messages and the hints, at ~1 ms per
  document. It lacks positions and a server.

## 3. Where the native parser spends its time

**Setup.** Input: the 60 `.rst` files of docutils 0.22.4's `docs/` (1.39 MB),
concatenated and repeated 15 times, giving 20.9 MB and 630,975 lines. Machine:
Apple Silicon, macOS 27. Build: Odin dev-2026-09 with `-o:speed`. A harness
calls `rst.parse_text` directly with a growing arena, best of 5. Sampling uses
`sample` at 1 ms on a `-debug -o:speed` build; ~3,080 samples fall in the parse.

| Measure | Value |
|---|---|
| `parse_text` | 386 ms, 54 MB/s, 3.95 G instructions (189 per byte) |
| of which `split_lines` | 51 ms (408 MB/s) |
| nodes | 815,866 (25.6 input bytes per node), `size_of(Node_Data)` = 96 |
| arena used | 242.6 MB (11.6× input), max RSS 158 MB |
| `docodin-check -j1` whole run | 0.36 s, RSS 175 MB; UTF-8 validation 12 ms (1.7 GB/s) |
| C ABI `docodin_parse` (parse + marshal) | 455 ms; wire 60.2 MB (2.9× input) |
| `marshal.loads` of that wire | 164 ms |
| wire tuple trees, 60 docs, Python heap | 9.1 MB = 6.5× input (stock docutils doctree: 62.3 MB = 44.8×) |
| largest real doc (124 KB `restructuredtext.rst`) | 1.7 ms parse |

Self time by function, as a share of parse samples:

| Hotspot | Share | Cause |
|---|---|---|
| `parse_inline` (with `search_initial` inlined) | 16.8 % | byte-at-a-time scan; every word start is a candidate |
| `simplename_ends` + its `memmove` | 19.3 % | the `name_` reference alternative runs at **every word start**; `Name_Ends` is a 520-byte struct returned by value and reversed |
| `uri_whole_at` + `implicit_inline` + `email_at` | 18.6 % | the standalone URI/e-mail search runs at every word start of every text run |
| `split_lines` + `normalize_line` + `rstrip` | 13.9 % | scalar `switch` per byte, a second pass counting `\n`, a third looking for tabs |
| `strings.join` + `memmove` | 4.0 % | `join_lines` copies paragraph lines that are contiguous in the source |
| other `memmove`/`memset` in the inliner | ~5 % | by-value `Inliner`/match structs, `escape2null` copies |
| `#soa` node append | 2.4 % | |
| block states (`classify`, `get_indented`, body/explicit/lists/tables) | ~10 % | |

**Experiment** (scratch copy, not committed). Three exact changes:

1. `search_uri` returns at once when the run has neither `:` nor `@`. An
   absolute URI needs `:` and an e-mail address needs `@`.
2. `match_reference` scans the ASCII simplename chain first. Without a `_`
   directly after a word run there can be no reference, so it records
   `name_fail` exactly as before and returns. Non-ASCII input takes the old path.
3. `split_lines`, `estimate_line_count` and `normalize_line` skip 16-byte blocks
   with `core:simd` (`lanes_eq` on the separator lead bytes, `reduce_min` over
   `select` for the offset).

| Variant | `parse_text` | Throughput | Instructions |
|---|---|---|---|
| 0.1.0 | 386 ms | 54 MB/s | 3.95 G |
| + inliner pre-filters (1, 2) | 249 ms | 84 MB/s | – |
| + SIMD line splitting (3) | 225 ms | 93 MB/s | 2.47 G |

`split_lines` alone went from 51 ms to 20 ms (1.05 GB/s). An FNV hash over
every node's kind, line, current line, numbers, links, text, raw and name is
**identical** in all variants.

After the change, the profile is 37 % `parse_inline` self time (the per-byte
candidate loop), 6.7 % copies, 5.7 % `implicit_inline`, 5.6 % `split_lines`
and 4.6 % node append. The next step is therefore a pulldown-cmark-style
candidate classifier for the inliner (section 6, item 1).

## 4. How reST differs from Python and Markdown

- **Indentation is structural, not lexical.** Python's INDENT/DEDENT is a
  token stream under a context-free grammar: a scanner with an indent stack
  suffices, and tree-sitter-python serializes just that stack. In reST the
  meaning of an indented block depends on the line *before* it: a literal
  block after `::`, a definition after a term line, an explicit-markup body
  after `..`, a field body after a field marker, a block quote (with optional
  `--` attribution) after a blank line. Blocks are cut out as line ranges
  (`get_indented`) and parsed recursively in nested state machines. A scanner with an indent stack, which is
  tree-sitter-rst's whole state, cannot reproduce this. The rst issues about
  lists, definition lists and literal blocks in section 2.2 are this mismatch.
- **Tokens depend on block context.** `*` at a line start is a bullet or
  emphasis. `1. Title` followed by `====` is a title, not a list. `..` is
  explicit markup or text. A lossless *token* stream in the ruff sense is not
  meaningful before block parsing. The lossless base layer for reST is the
  **line table**: offset, indent, blank flag, tab flag.
- **Not context-free.** Section levels come from the order in which title
  styles first appear; an enumerated list continues only while ordinals are
  sequential and style and format match; anonymous references pair with
  anonymous targets by document order; auto-numbered footnotes and `make_id`
  counters follow document order.
- **Inline markup is regex-defined.** Unlike CommonMark's delimiter stack, reST
  inline markup does not nest. Recognition uses start-string prefix and
  end-string suffix character classes (Unicode punctuation categories), a
  greedy `simplename` with backtracking over its possible ends, and a leftmost
  match over many alternatives. Linear time needs memo tables (docodin's
  `no_end`, `name_fail`, `role_fail`, `email_fail`), not an openers stack. What
  does carry over from Markdown is the **two-phase shape**: blocks first, then
  inlines per text block, and the SIMD candidate scan.
- **Positions need a mapping.** docutils works on `string2lines` output: tabs
  expanded to 8-column stops, `\v` and `\f` turned into spaces, trailing
  whitespace stripped, and Unicode line separators honoured. Columns in
  expanded lines are not source columns. Two useful facts: `split_lines`
  already returns zero-copy input slices for lines without tabs (source offsets
  follow from the pointer), and `escape2null` preserves length (inline offsets
  map 1:1 onto the joined text block).

## 5. An incremental strategy for reST

### 5.1 Safe reparse boundaries

An **anchor** is a non-blank line at column 0 whose previous line is blank, or
the first line. At an anchor between top-level constructs the root `Body`
machine carries almost no state: `line_offset`, `frozen_line` (0 outside
list-like constructs), `cur_line` (derived from the position) and `inserted`
(include lines). That is the reST equivalent of tree-sitter's "external scanner state equal".
An anchor is a **boundary**, where the previous construct cannot continue, unless:

- the previous top-level construct is **list-like**, because docutils looks
  past blank lines for its next item: bullet lists (same bullet), enumerated
  lists (next ordinal, same style and format), field and option lists,
  definition lists (a term at column 0 after a blank line), and explicit-markup
  runs (`explicit_list`: consecutive footnotes, targets, directives, comments);
- the previous construct is a **simple table**, whose rows and borders may be
  separated by blank lines at column 0;
- the previous paragraph ends in **`::`**, because the next column-0 block
  after the blank line may be a *quoted* literal block, or produce "Literal
  block expected; none found."

Local, with no special case: block quotes with attributions, indented literal
blocks, directive and field bodies (indented, so inside the window up to the
next anchor), and section titles with or without overline and transitions (one
construct starting at the anchor; their *placement* errors come from the host
or from transforms).

A construct also peeks ahead (`blank_finish`, title underlines, "Unexpected
indentation."). The exact analogue of tree-sitter's `lookahead_bytes` is to
record, per top-level construct, the furthest line its state machine read (the
`next_line` high-water mark). A construct is reusable only if that mark lies
before the edit.

### 5.2 Non-local state (recompute, never patch)

| State | Where docodin keeps it | Strategy |
|---|---|---|
| title style order, section levels, "Title level inconsistent" | host: `builder.py`, `odin/reader`, `odin/check` (`title_styles`); the parser only emits flat `Section_Title` events | re-run the O(titles) pass over events after each parse |
| enumerated list sequence | inside one list construct | covered by the list-like rule above |
| explicit and implicit targets, duplicates, `ids`/`make_id` counters, message ids | host registry, in document order | rebuild per parse; O(n) and cheap |
| anonymous references ↔ anonymous targets | order-matched, document-wide | rebuild; definition = n-th anonymous target |
| auto-numbered and symbol footnotes, citations, substitutions | host and transforms | rebuild |
| `include` | lines inserted into the state machine | the included file is an input dependency (salsa-style) |
| absolute `line` / `cur_line` on nodes, `Directive_Info` offsets | parse tree | shift by Δlines on splice (`cur_past_end` encodings too) |

### 5.3 Subtree reuse over `rst.Tree`

- **Contiguity.** Nodes are appended to the `#soa` array in parse order, and
  nested parses and the inliner run inside their construct. Each top-level
  construct is therefore a contiguous handle range, plus ranges of `phrases`
  and `directives`. This is to be asserted in tests, not assumed.
- **Algorithm**, tree-sitter's reuse in reST's terms:
  1. Map the edit to lines, then walk back to the previous *boundary* whose
     construct's lookahead mark precedes the edit. Take one more construct as
     margin: messages such as "Unexpected indentation." are created while
     parsing the next construct.
  2. Parse forward from there with `input_offset` set, so lines come out
     absolute.
  3. After each completed top-level construct, check for convergence: if the
     current line equals an old boundary shifted by Δ, lies past the edit, and
     the construct just finished is closed, stop.
  4. Splice. Copy the old tail ranges with handles relocated (+Δh on
     `parent`/`first`/`last`/`next`/`extra`), lines shifted by Δlines, and string
     views rebased by Δbytes.
- **Alternative.** A rowan-style "green block" layer, with block-relative lines
  and offsets and absolute positions computed on access, makes reuse zero-copy.
  But it changes every consumer: the serializer, `builder.py`, `odin/reader` and
  `odin/check`. Keep absolute positions in `rst.Tree` and do the relocation in
  the editor layer only.
- **When it pays.** A full parse is ~11 µs per KB after item 1 (0.1.0: ~19 µs).
  Reuse matters only above ~1 MB per file, which is rare for reST. That is the
  same conclusion rust-analyzer and ruff reached.

## 6. Proposed 0.2.0 improvements, ranked

The ranking weighs benefit against cost and risk. For every item, **what must
not change** is the same:

- docutils' output, messages and line numbers;
- node `source`/`line`;
- the wire format that `builder.py` consumes, unless a new flag asks for more;
- the result of every differential suite.

| # | Item | Benefit | Cost | Fidelity risk |
|---|---|---|---|---|
| 1 | (d) inliner fast paths and SIMD scanning | 1.7× measured, ~2–2.5× expected | small | low–medium, tested |
| 2 | (a) lossless position layer | enables 3 and 5 | medium | none (behind a flag) |
| 3 | (c) `docodin-lsp` | exact reST diagnostics and navigation in every editor | large | none (read-only) |
| 4 | (e) lower peak memory | most of the +109 MB RSS gap (to confirm) | small → medium | none |
| 5 | (b) incremental reparse API | only for files over ~1 MB | medium | none on the docutils path |
| 6 | (f) line table first, `dump --spans`, tree-sitter-rst oracle | tooling | small | none |

### 1. Inliner fast paths and SIMD scanning (d)

- **What.**
  - Land the three measured changes from section 3.
  - Replace `search_initial`'s per-byte loop with a candidate scanner. A
    16-byte `core:simd` classifier (`runtime_swizzle` nibble tables, or
    `lanes_eq` over `` * ` _ | [ : ``) finds the next special byte, and the
    `name_` alternative is tried only at the start of a word chain that reaches
    a `_`.
  - Add a whole-text pre-filter: text with no special byte and no `:` or `@`
    becomes a single Text node.
  - Return `Name_Ends` (520 bytes) through a pointer instead of by value.
  - In `join_lines`, return the source slice when the lines are contiguous and
    separated by `\n`.
  - Optionally, validate UTF-8 in `docodin-check` with the Keiser–Lemire
    method.
- **Benefit.** Measured 386 → 225 ms (1.7×). The candidate scanner targets the
  remaining 37 % of the time. The shim path gains too: the native parse is
  ~85 % of `docodin_parse`, and ~60 % of `docodin_parse` plus `marshal.loads`.
- **Cost.** Mostly `inline.odin` and `source.odin`; days, not weeks.
- **Fidelity risk.** When candidates are skipped, the leftmost-match semantics
  of docutils' `initial` regex must still hold. Risky cases are non-ASCII
  alphanumerics, `\x00` escapes and `character_level_inline_markup`.
- **Verification.**
  - A parse-tree hash (as in section 3) exposed as a debug option of
    `docodin-check`, compared before and after on the corpus and the fuzz
    corpora.
  - `tests/fuzz_differential.py` with a generator biased toward URIs, e-mail
    addresses, `name_` chains, non-ASCII words and escapes.
  - docutils' suite, native and with `DOCODIN_NATIVE=0`.
  - A timed pathological suite in the style of cmark's: long `a-b-c…` chains,
    10⁵ `*`, 10⁵ `` ` ``.

### 2. Lossless position layer (a)

- **What.**
  - `split_lines` also produces a **line table**. Per line it records the source
    byte start, content length, terminator length and a has-tab flag, plus a
    column map for lines with tabs.
  - Under a new `Parse_Flag.Spans`, a `spans` array parallel to `Tree.nodes`
    holds `{start, end: u32}` source byte offsets:
    - block nodes get the extent of their lines;
    - inline nodes are mapped through their text block's line starts, which is
      exact because `escape2null` keeps lengths.
  - A ruff-style `LineIndex` converts offsets to UTF-8, UTF-16 or UTF-32
    line/column pairs, with an ASCII fast path.
  - Optionally, `Node_Data` shrinks from 96 to ~64 bytes by storing
    `text`/`raw`/`name` as `u32` offset and length. That also makes splice
    rebasing trivial.
- **Benefit.** Folding, semantic tokens, code actions, column-precise
  diagnostics, and items 3 and 5.
- **Cost.** Medium. The hard cases are nested parses, table cells
  (`line_delta`), substitution definitions (dropped lines) and include
  insertion.
- **Fidelity risk.** None with spans off. Nothing on the docutils path reads
  the array.
- **Verification.**
  - The tree hash is equal with and without `.Spans`.
  - Fuzzed invariants:
    - children lie inside their parents;
    - siblings are ordered and disjoint;
    - `source[span]` equals the text of escape-free Text nodes after tab
      normalisation;
    - the first line of a span equals `node.line` wherever docutils sets one.

### 3. `docodin-lsp`, a native language server (c)

- **Architecture**, modelled on ruff server: JSON-RPC over stdio
  (`core:encoding/json`); a main-loop thread owns the session and handles
  notifications synchronously; requests run on a worker pool over immutable
  snapshots (an arena plus its parse); incremental text sync through the
  `LineIndex`; a **full reparse** per change (1–2 ms); pull diagnostics with a
  push fallback.
- **Features.**
  - *Diagnostics*:
    - Sources: `check.check_text`, plus the native reader's registry messages
      (duplicate targets, unknown and anonymous references) in plain-docutils
      projects.
    - Elm titles and hints become the message and `codeDescription`.
    - Mechanical fixes become code actions, carried in `data` as in ruff: fix
      the underline length, insert a blank line, escape an unmatched
      start-string, add a missing underline, expand tabs.
  - *documentSymbol*: sections, with levels from the title-style pass.
  - *foldingRange*: sections, directives, lists, literal blocks, comments and
    tables.
  - *definition*, *references* and *rename* for:
    - explicit and implicit targets, matched with `fully_normalize_name`;
    - footnotes of every kind, citations and substitutions;
    - anonymous references, matched by order.
  - *hover*: substitution definitions, footnote and citation text, target URIs,
    and directive and role documentation from generated tables.
  - *semanticTokens*: inline kinds, roles, directive names, field and option
    markers, adornments, comments.
  - *completion*: directives and their options, roles, reference names,
    substitutions and footnote labels.
  - *Cross-file*: a per-file map-reduce index for `:ref:`/`:doc:`. The whole
    docs tree used here checks in 10–20 ms. Sphinx directives, roles and labels
    come from an optional manifest that a docodin Sphinx extension writes, so
    the server never runs Python, unlike esbonio.
- **Benefit.** Docutils-exact diagnostics as you type in every LSP editor, and
  the first reST server with semantic tokens, folding and references.
- **Cost.** Large: ~3–5k lines of Odin. Needs item 2.
- **Fidelity risk.** None; the server only reads.
- **Verification.** Golden recorded sessions; diagnostics equal
  `docodin-check` on the corpus.
  - Definitions are checked against docutils: for each `reference` with a
    `refid` in the transformed doctree (`scripts/doctree_json.py`), the LSP
    must answer with that target's span.
  - Symbols are compared with docutils' section tree.
  - CI budget: p99 from `didChange` to diagnostics under 10 ms on a 124 KB
    document.

### 4. Lower peak memory (e)

- **Facts.** The arena uses 11.6× the input, and the node reserve (`len/10` ×
  96 B = 9.6 B per input byte) is 2.5× what is used. The wire (2.9× the input)
  briefly exists twice because `ctypes.string_at` copies it, and the tuple tree
  adds 6.5× the input before `builder.py` builds nodes. The per-thread bump
  arena keeps a block of up to 64 MB.
- **Hypothesis, to confirm.** The +109 MB peak RSS at equal retained memory
  comes from millions of short-lived tuples interleaved with long-lived nodes:
  pymalloc arenas that cannot be returned to the OS.
- **What.**
  1. Run `marshal.loads` on a ctypes view of the native buffer
     (`(c_char * n).from_address(ptr)`), not on a copy.
  2. Size the node reserve by measurement.
  3. Cap the retained block, for example at 8 MB.
  4. Stream the wire per top-level construct, so the whole tuple tree never
     exists at once.
  5. Shrink `Node_Data` (item 2).
- **Cost.** Steps 1–3 are small. Step 4 is medium and touches `builder.py`.
- **Fidelity risk.** None. Step 4 changes when Python objects are created, not
  the node order.
- **Verification.** Peak RSS (`/usr/bin/time -l`) and `tracemalloc` peaks per
  step in a fixed harness; a fixed Sphinx project at release time;
  `test_sphinx.py` and the shim differential suites.

### 5. Incremental reparsing API (b)

- **What.** `rst.reparse(old, edit)` implementing the boundary, lookahead and
  convergence rules of section 5. It also returns the changed ranges, for
  semantic-token deltas. Registries and section levels are always rebuilt.
- **Benefit.** Only for files over ~1 MB, where a full reparse exceeds ~10 ms.
- **Cost.** Medium, with a large correctness surface.
- **Fidelity risk.** None on the docutils path, which always parses fully.
- **Verification.** Randomised edits on fuzz documents, like tree-sitter-rst's
  new `test_incremental.py`: `reparse` and a full parse must give the same tree
  hash and messages. Ship behind a size threshold.

### 6. Other adoptions (f)

- **Line table first** is the reST analogue of ruff's lossless `Tokens`. A full
  token-stream redesign is not worth it: block states are only ~10 % of the
  time.
- **`docodin dump --json --spans`** exposes the parse tree with positions to
  other tools, such as esbonio and linters.
- **tree-sitter-rst as a consumer, not a model.** No tree-sitter grammar can
  reach docutils fidelity (section 4). docodin can instead serve as a
  differential oracle for its sections, lists and tables.
- **Rejected:** parallel parsing of one document at anchors (files are already
  parsed in parallel), and a refcounted green tree (the `#soa` handle tree is
  already where ruff's node indices and pulldown-cmark's index trees converge).

## 7. Suggested order of work

1. Item 1 (speed): land it first. It changes no interfaces, and the tree-hash
   check becomes a permanent CI guard.
2. Item 2 (positions), then `docodin dump --spans`.
3. Item 4, steps 1–3 (memory quick wins); measure; then step 4 if the gap
   remains.
4. Item 3 (`docodin-lsp`): diagnostics, symbols, folding and semantic tokens
   first, then definition, hover and completion, then the Sphinx manifest.
5. Item 5 (incremental) only if LSP telemetry shows files where a full reparse
   exceeds its latency budget.
